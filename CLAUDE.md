# ML_labs — лабораторні роботи з моделювання ШІ

Проєкт для виконання п'яти лабораторних робіт (завдання — `labs/labNN/ASSIGNMENT.md`,
оригінали PDF — у батьківському каталозі). Стек: Python 3.12, TensorFlow/Keras
(нейромережі), scikit-learn (класичне ML), керування середовищем — `uv`.

## Для кого це робиться

Автор — Java-інженер, новачок у Python і машинному навчанні. Тому:

- пояснюй терміни ML і конструкції Python простими словами, де доречно — через аналогії з Java;
- код пиши в «Java-стилі»: класи з однією відповідальністю, інтерфейси (`Protocol`/`ABC`),
  незмінні `@dataclass(frozen=True)`, залежності через конструктор, жодної «магії»;
- спілкуйся українською.

## Команди

```bash
uv run mllabs doctor      # перевірка середовища
uv run mllabs list        # стан лабораторних
uv run mllabs new N       # каркас лабораторної №N (з ASSIGNMENT.md)
uv run mllabs run N       # виконати код -> labs/labNN/artifacts/
uv run mllabs report N    # report.md -> labs/labNN/report/Звіт_ЛРN.pdf
uv run ruff format . && uv run ruff check .   # стиль
uv run pytest             # тести
uv add <пакет>            # нова залежність (НЕ pip install)
```

## Структура

```
src/mllabs/core/        фреймворк: Lab, Step, LabContext, ArtifactStore, шляхи
src/mllabs/reporting/   Markdown -> HTML -> PDF за шаблоном кафедри
src/mllabs/scaffold/    генератор каркаса (mllabs new)
src/mllabs/labs/labNN/  КОД лабораторної №N
labs/labNN/             МАТЕРІАЛИ лабораторної: ASSIGNMENT.md, PLAN.md, GUIDE.md,
                        artifacts/ (графіки, таблиці, metrics.json), report/
data/raw, data/processed   датасети (processed передаються між лабораторними)
config/report.toml      дані титульної сторінки
tests/                  pytest
```

Код, потрібний кільком лабораторним (завантаження датасету, препроцесинг із ЛР1 для ЛР2–3,
модель із ЛР4 для ЛР5), виноситься у спільний пакет `src/mllabs/<домен>/`
(наприклад `mllabs/data/`), а не копіюється і не імпортується з чужого `labs/labNN`.

## Як виконується лабораторна

Запуск: `/lab N` (скіл `lab`) — він веде весь конвеєр і викликає агентів:

1. `lab-planner` → `PLAN.md` (чекліст вимог, вибір датасету/моделей, перелік модулів і артефактів)
2. `ml-engineer` → код + тести + артефакти
3. `ml-reviewer` → перевірка коректності ML і якості коду (лише читає)
4. `tutor` → `GUIDE.md` (навчальний конспект для автора)
5. `report-writer` → `report.md` + PDF

Лабораторна **готова**, коли: кожна вимога з `PLAN.md` закрита; `ruff` і `pytest` зелені;
`mllabs run N` проходить з нуля; є `GUIDE.md`; PDF зібрано й переглянуто очима.

## Обов'язкові правила

**Код** (деталі — скіл `python-style`):
- анотації типів і docstring (Google-стиль, українською) на всьому публічному; ідентифікатори — англійською;
- `lab.py` лише оркеструє кроки (`Step`), логіка — в окремих модулях пакета, числа — в `config.py`;
- шляхи тільки через `ProjectPaths`/`LabPaths`; результати тільки через `ArtifactStore`; `logging`, не `print`.

**Коректність ML**:
- фіксований seed (`LabContext.seed`), стратифіковане розбиття для класифікації;
- усе, що «вчиться» на даних (імп'ютери, скейлери, енкодери, SMOTE), робить `fit` лише на train —
  використовуй `Pipeline` (для SMOTE — `imblearn.pipeline.Pipeline`); тестові дані не аугментуються;
- метрики рахуються на відкладених даних; для дисбалансу accuracy не головна метрика.

**Звіт і конспект** (скіли `lab-report`, `lab-guide`):
- жодної цифри «з голови»: числа — через `{{metrics...}}` або CSV-таблиці з `artifacts/`;
- висновки мають спиратися на реально отримані результати, навіть якщо вони «некрасиві».

**Інше**: не коміть і не пуш без прохання; важкі залежності (PyTorch/Anomalib для ЛР4) і
вибір датасету погоджуй з автором.
